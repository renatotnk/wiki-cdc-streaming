# SPEC — Phase 2: Bronze (Spark Declarative Pipelines)

**Depends on:** `SPEC-agnostic-architecture.md` (`StorageBackend` contract, principles P1–P8, conventions 9.1–9.5.1) and `SPEC-phase1-ingestion.md` (raw format and partitioning).
**Does not redecide anything already fixed in those documents — only references them.**

**Revision note:** this SPEC was updated during implementation after empirically testing `pyspark[pipelines]` against real Spark 4.1.1/4.2.0 and a real local MinIO instance. Several of the original draft's assumptions about Spark Declarative Pipelines (SDP) turned out not to hold in the open-source distribution. Sections 4, 5, 7, 8, 9, 11, 12, 13, and 14 were corrected accordingly — see Section 4.1/4.2/4.3 for what changed and why.

---

## 1. Objective

Declare the raw Parquet files generated by Phase 1 as a bronze streaming table via Spark Declarative Pipelines (SDP) — typed, idempotent by construction, with Change Data Feed enabled — and add a second, genuinely external reference dimension (`bronze_dim_wiki_reference`) refreshed in batch whenever a new snapshot file arrives. Both run identically via `spark-pipelines run` locally and as a Lakeflow Declarative Pipeline on Databricks, in Python or SQL.

## 2. Scope

**In scope:**
- `bronze_recentchange` as an SDP streaming table reading the partitioned raw data.
- `bronze_dim_wiki_reference` as an SDP batch/streaming table reading periodic wiki-metadata snapshots from the Wikimedia sitematrix API.
- Explicit schema/typing for both, per `contracts/bronze_recentchange.contract.yaml` and the new `contracts/dim_wiki_reference.contract.yaml` (P8).
- Change Data Feed enabled on `bronze_recentchange` from table creation.

**Out of scope:**
- *Business* schema validation and routing of invalid rows (Phase 3 — bronze is a faithful mirror of raw, it does not filter by business rule).
- Any row-level content check, including the kind of thing SDP's native "expectation" feature would express — see Section 4.1: that feature isn't used in this phase at all, not even conditionally.
- Consuming the Change Data Feed (that's Phase 3 — here we only enable the property on the table).
- Aggregations (Phase 4, deferred).

## 3. Why a second, external dimension source at bronze

Every dimension in the star schema so far (`dim_editor`, `dim_page`, `dim_wiki`) is *derived* entirely from the fact stream itself — there's no dimension coming from a genuinely independent source, which is a bit artificial next to a real Kimball scenario (where dimensions commonly arrive from different systems, on their own refresh cadence). `bronze_dim_wiki_reference` fixes that: it holds wiki metadata (language name, project type — Wikipedia, Wiktionary, Wikinews, etc.) sourced from the Wikimedia `sitematrix` API (`https://meta.wikimedia.org/w/api.php?action=sitematrix`), a real reference dataset independent of the `recentchange` event stream. `dim_wiki` in gold (Phase 4) is enriched by joining the stream-derived `wiki_code` against this table — a genuine conformed-dimension-from-a-second-source pattern, not just a label for the same data twice.

### 3.1 How new snapshots arrive and get picked up

`scripts/fetch_wiki_sitematrix.py` (a one-off/periodic script, not part of the pipeline itself) calls the sitematrix API and drops a timestamped JSON snapshot into **`dim_wiki_reference/`** — a top-level bucket prefix, a *sibling* of `raw/`, not nested inside it. `bronze_dim_wiki_reference` is declared as a batch table over that folder — every `spark-pipelines run` picks up any new snapshot file automatically (SDP's incremental file-source semantics, the same mechanism as `bronze_recentchange`, just triggered by an irregular/manual file drop instead of continuous producer output). No separate mechanism is needed for "batch on file arrival" — it's the same SDP dataset declaration pattern used for the streaming table, just over a folder that fills up occasionally instead of continuously.

**Discovered constraint:** an earlier draft nested this under `raw/dim_wiki_reference/`, matching the phrasing "drops a snapshot into raw/dim_wiki_reference/". That breaks `bronze_recentchange`: it reads the *entire* `raw/` tree (`spark.readStream.load(resolve_uri("raw"))`), and Spark's Hive-partition discovery walks that whole tree looking for a consistent `dt=.../hour=.../` structure — a sibling subdirectory named `dim_wiki_reference/` that doesn't match that pattern makes it fail immediately with `[CONFLICTING_DIRECTORY_STRUCTURES]`, verified empirically running both datasets together. Since Phase 1's `raw/dt=.../hour=.../` layout is already implemented and out of scope to change, `dim_wiki_reference/` moved to its own top-level prefix instead — a completely separate tree Spark has no reason to conflate with `raw/`.

## 4. Why bronze isn't "just copying raw"

Bronze applies **typing** (schema-on-write) via an explicit Spark schema declared in `pipelines/bronze/schema.py` — every column gets its contracted type, matching `contracts/bronze_recentchange.contract.yaml` and `contracts/dim_wiki_reference.contract.yaml`. It applies **no business rule**: row-level content validation is exclusively Phase 3's (silver's) responsibility, per the architecture SPEC's P4 invariant. If a raw file's actual on-disk column types genuinely conflict with the declared schema, Spark's own schema enforcement already fails the read — this is a side effect of typing, not a designed mechanism, and it does not enforce arbitrary row-level constraints (e.g., "`_event_id` must not be null" is *not* checked here — see 4.1).

### 4.1 Discovered constraint: SDP expectations are not used in this phase

The original draft of this SPEC called for `@dp.expect_or_fail`/`CONSTRAINT ... EXPECT ... ON VIOLATION FAIL UPDATE` to express a fail-fast structural check. During implementation this turned out not to exist in open-source Apache Spark. Verified empirically against both `pyspark[pipelines]==4.1.1` (the version pinned in this project) and `4.2.0` (the latest stable release at the time of writing):

- `pyspark.pipelines`'s public API exports no `expect`/`expect_or_fail`/`expect_or_drop` in either version.
- No `Expectation`/`Constraint` class exists anywhere in the compiled `spark-pipelines` jar for either version.
- The SQL `CONSTRAINT ... EXPECT ...` syntax throws a `ParseException` at registration time.
- Worse than a soft degradation: since `spark-pipelines` imports every matching Python file into *one* shared dataflow graph, a file using `@dp.expect_or_fail` raises `AttributeError` at import time and crashes registration for the **entire pipeline spec**, not just that one dataset — nothing in Phase 2 would dry-run or run locally at all.

Expectations are a genuine, documented Databricks Lakeflow Declarative Pipelines feature — this gap is specific to the open-source Spark distribution, not a misunderstanding of Databricks' own capability. Since this project must run smoothly both locally (OSS Spark) and inside Databricks from the *same* source files (P1/P6), and since bronze's job here is limited to materializing raw data as a typed Delta table, **Phase 2 does not use SDP expectations at all — not even conditionally, not even via a compatibility shim.** All row-level/content validation (the 6 DQ dimensions, `_event_id IS NOT NULL`-style checks) is deferred entirely to Phase 3, where the architecture SPEC (P4, Section 4.4) already places that responsibility.

### 4.2 Discovered constraint: `bronze_recentchange` is Python-only

Declaring a *streaming* source directly over an arbitrary raw file path is also a Databricks-only capability in SQL: `read_files(...)` as a table-valued function, and the `STREAM <path>` pattern for turning a batch relation into a streaming one, are both absent from open-source Spark's SQL grammar. Verified empirically:

- `read_files(...)` → `[UNRESOLVABLE_TABLE_VALUED_FUNCTION]`.
- `STREAM parquet.\`path\`` parses, but the pipeline runtime rejects it at execution time with `[INVALID_FLOW_QUERY_TYPE.BATCH_RELATION_FOR_STREAMING_TABLE]` — `parquet.\`path\`` resolves as a batch relation, and `STREAM` doesn't convert it.

Only Python's `spark.readStream.format(...).load(path)` can create a genuine streaming relation from a raw folder in OSS Spark. Because of this, **`bronze_recentchange` (Section 7.1) is implemented in Python only — no SQL variant is provided for this one dataset.** Convention 9.5.1's "both variants, pick one" therefore applies only to `bronze_dim_wiki_reference`, which is a *batch* materialized view and has no such restriction (Section 7.2/7.3 use `json.\`path\`` — standard Spark SQL, not `read_files`).

### 4.3 Discovered constraint: local runs need a persistent local metastore and Hadoop connector setup

Two more things, verified empirically against a real local MinIO instance, that the original draft didn't anticipate:

1. **`spark-pipelines run` uses a purely in-memory catalog by default.** No `metastore_db` is created anywhere, so a *second, separate* CLI invocation has no memory of tables a prior invocation created — even though the underlying Delta files on disk persist. Re-running produces `[LOCATION_ALREADY_EXISTS]` instead of the incremental append acceptance criterion #2 requires. Fix: `spark.sql.catalogImplementation=hive` in `SPARK_CONF_DIR`/`spark-defaults.conf` (this — not the pipeline spec's own `configuration:` block — because it's a "static" Spark config that can only be set before the JVM/session boots; the `spark-pipelines` launcher already has a session running by the time `spec.configuration` is applied, so setting it there throws `CANNOT_MODIFY_STATIC_CONFIG`). This corrects Section 14's original "no local Hive Metastore is created" — a local, embedded, zero-cost metastore turned out to be necessary for repeatable local runs, not optional complexity.
   - The embedded Derby metastore's **own** location (`metastore_db/`, `derby.log`) can't be redirected via `javax.jdo.option.ConnectionURL` in `spark-defaults.conf`, though: that file's loader only accepts keys prefixed `spark.` and silently drops anything else with an easy-to-miss `Ignoring non-Spark config property` warning — verified empirically. Derby therefore always creates `metastore_db`/`derby.log` relative to whatever directory `spark-pipelines` is invoked *from*, not a configurable path. Practical consequence: always run `spark-pipelines` commands from the repo root (`docs/RUNBOOK.md` does), and both are gitignored there. `spark.sql.warehouse.dir` (correctly `spark.`-prefixed) is unaffected and works as expected — table **data** does land at the configured path, only the metastore's own bookkeeping location doesn't.
   - The same "silently drops non-`spark.`-prefixed keys" behavior also applies to `spark-pipeline.yml`'s own `configuration:` block (verified: an unprefixed custom key like `raw_dim_wiki_reference_path` triggers the identical warning and never reaches `spark.conf`, so a SQL file's `${raw_dim_wiki_reference_path}` substitution silently fails to resolve). Every custom configuration key in this project is therefore namespaced `spark.wikicdc.*` — see Section 7.3/7.4/8.
2. **Reading `s3a://`/`gs://` from Spark needs the Hadoop connector jar and credentials wired in separately from Phase 1's `StorageBackend`.** Phase 1 never needed this — `S3CompatibleStorageHandler`/`GcsStorageHandler` talk to MinIO/S3/GCS via their own SDKs (`minio`, `google-cloud-storage`), not through Spark's Hadoop filesystem layer. Spark needs `spark.jars.packages` (the `hadoop-aws` connector + AWS SDK bundle) and `spark.hadoop.fs.s3a.*` (endpoint/credentials/path-style) — the connector jar is also a "static", JVM-boot-time setting, so it goes in the same `spark-defaults.conf`, not the pipeline spec. This is genuinely new surface for Phase 2, not a reuse of anything Phase 1 already built.
3. **A genuine Delta table needs Delta's own SparkSession extension/catalog, and must *not* be told `format="delta"` explicitly on the `@dp.table`/`@dp.materialized_view` decorator.** Two separate things had to be true, both verified against a real local MinIO instance:
   - Without `spark.sql.extensions=io.delta.sql.DeltaSparkSessionExtension` + `spark.sql.catalog.spark_catalog=org.apache.spark.sql.delta.catalog.DeltaCatalog` + `spark.sql.sources.default=delta` (all "static", JVM-boot-time settings — same `spark-defaults.conf` as items 1/2), a table declared with `table_properties={"delta.enableChangeDataFeed": "true"}` silently materializes as **plain Parquet** (a `_spark_metadata` sink, no `_delta_log` at all) — the property is a no-op, CDF is not actually enabled.
   - Passing `format="delta"` *explicitly* to the decorator (rather than relying on `spark.sql.sources.default=delta` alone) works for a table's first creation, but a **second, separate** `spark-pipelines run` against the same persistent Hive metastore then fails with `[DELTA_CANNOT_CHANGE_PROVIDER] 'provider' is a reserved table property, and cannot be altered` — reproduced with a 3-line minimal example, independent of any project-specific code, and independent of `pyspark` patch version (4.1.1 and 4.1.3 both hit it). Omitting `format=` and relying solely on `spark.sql.sources.default=delta` avoids this: verified across three separate `spark-pipelines run` invocations (initial load, a content-free rerun, and a rerun with a genuinely new file), all succeeding, with correct row counts and no duplication each time.

`scripts/render_local_spark_config.py` (new, not originally in Section 10) generates this local `spark-defaults.conf` from the same `.env` variables `S3CompatibleStorageHandler`/`GcsStorageHandler` already read (`STORAGE_BACKEND`, `S3_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, etc.) — see Section 10 and `docs/RUNBOOK.md` for the exact local setup steps. This keeps the credential-management convention (9.8) intact: the generated file is gitignored, never committed, and holds no value that isn't already in `.env`.

The **raw data path itself** (`raw_recentchange_path`, resolved via `StorageBackend.resolve_uri`) does *not* need any of this — `bronze_recentchange.py` and `dim_wiki_reference.py` call `get_storage_backend().resolve_uri(...)` directly as plain Python, exactly like the producer/consumer already do (reusing Phase 1's factory, per Section 4.2 of the architecture SPEC). This only became a question for `dim_wiki_reference.sql`, since a SQL file can't call Python — see Section 7.4.

## 5. Why SDP instead of hand-rolled Structured Streaming (recorded here, detailed in `trade-offs.md`)

Earlier drafts of this SPEC used a custom `BaseDeltaIngestor`/`BronzeIngestor` class with manual `readStream`/`writeStream`/`Trigger.AvailableNow`/checkpoint wiring. SDP replaces all of that: declaring `bronze_recentchange` as a streaming table gives the same incremental, checkpoint-backed, run-and-stop behavior natively, with less code to maintain — and, critically, the core SDP dataset-declaration model (`@dp.table`/`@dp.materialized_view`, the dataflow graph, incremental file-source discovery) is genuinely open-source (Spark 4.1+, `pyspark.pipelines`/`spark-pipelines` CLI), so this doesn't cost anything in local/cloud portability for that core model (P1/P6). **Caveat, discovered during implementation (Sections 4.1/4.2):** expectations, `read_files`, and (as of 4.1.1) `create_auto_cdc_flow` are Databricks Lakeflow extensions not yet contributed back to OSS Spark — `create_auto_cdc_flow` did land in the 4.2.0 release, but expectations and `read_files` had not, as of the versions tested here. Phase 2 works around this by not depending on either feature (Sections 4.1/4.2); Phase 4 will need to re-check `create_auto_cdc_flow`'s availability against whatever PySpark version is current at that time. See `docs/trade-offs.md` for the full comparison.

## 7. Pipeline definitions

### 7.1 Python (`pipelines/bronze/bronze_recentchange.py`) — the only variant for this dataset (Section 4.2)

```python
from pyspark import pipelines as dp
from pyspark.sql import SparkSession
from pyspark.sql.functions import current_timestamp

from pipelines.bronze.schema import BRONZE_RECENTCHANGE_SCHEMA
from src.shared.backend_factory import get_storage_backend

spark = SparkSession.active()
raw_recentchange_path = get_storage_backend().resolve_uri("raw")

@dp.table(
    name="bronze_recentchange",
    # No explicit format="delta" (Section 4.3, item 3) -- relies on
    # spark.sql.sources.default=delta (local-stack/.spark-conf/spark-defaults.conf)
    # for genuine Delta materialization instead; passing format="delta"
    # explicitly here works for the first run but breaks every subsequent
    # separate `spark-pipelines run` with [DELTA_CANNOT_CHANGE_PROVIDER].
    table_properties={"delta.enableChangeDataFeed": "true"},
    partition_cols=["dt", "hour"],
)
def bronze_recentchange():
    return (
        spark.readStream.format("parquet")
        .schema(BRONZE_RECENTCHANGE_SCHEMA)
        .load(raw_recentchange_path)
        .withColumn("_bronze_loaded_at", current_timestamp())
    )
```

No `@dp.expect_or_fail` (Section 4.1). No SQL variant (Section 4.2). `dt`/`hour` are not in `BRONZE_RECENTCHANGE_SCHEMA` — Spark discovers them automatically from the `dt=.../hour=.../` folder structure Phase 1 already writes. Genuine Delta materialization (verified: `_delta_log` present, CDF enabled, correct row counts across 3 separate runs including a content-free rerun) depends entirely on `spark-defaults.conf` (Section 4.3, item 3) — Delta's own SparkSession extension/catalog must be registered, and `format=` must be left unset on the decorator.

### 7.2 Discovered constraint: both variants can't share the table name at the same time

Unlike `bronze_recentchange` (Python-only, no conflict), both `dim_wiki_reference.py` and `dim_wiki_reference.sql` genuinely exist side by side per convention 9.5.1. Declaring both under the *same* table name in the *same* pipeline glob fails registration outright: `spark-pipelines` rejects two flows targeting one output name in a single dataflow graph (`[PIPELINE_DUPLICATE_IDENTIFIERS.OUTPUT]`, verified empirically with a minimal example — one `.py` and one `.sql` file, both declaring the same name). So the committed files use `bronze_dim_wiki_reference_py` / `bronze_dim_wiki_reference_sql` instead of the shared final name — once you've picked a variant, rename its table back to `bronze_dim_wiki_reference` and delete the other file, exactly as convention 9.5.1 already asks ("once you decide which to keep, delete the other").

### 7.3 Python (`pipelines/bronze/dim_wiki_reference.py`)

```python
from pyspark import pipelines as dp
from pyspark.sql import SparkSession

from pipelines.bronze.schema import DIM_WIKI_REFERENCE_SCHEMA
from src.shared.backend_factory import get_storage_backend

spark = SparkSession.active()
raw_dim_wiki_reference_path = get_storage_backend().resolve_uri("raw/dim_wiki_reference")

@dp.materialized_view(name="bronze_dim_wiki_reference_py")  # rename to bronze_dim_wiki_reference once chosen (Section 7.2)
def bronze_dim_wiki_reference_py():
    return (
        spark.read.format("json")  # batch, not readStream — new snapshots arrive irregularly
        .schema(DIM_WIKI_REFERENCE_SCHEMA)
        .load(raw_dim_wiki_reference_path)
    )
```

### 7.4 SQL (`pipelines/bronze/dim_wiki_reference.sql`)

```sql
CREATE MATERIALIZED VIEW bronze_dim_wiki_reference_sql AS  -- rename to bronze_dim_wiki_reference once chosen (Section 7.2)
SELECT
  CAST(wiki_code AS STRING) AS wiki_code,
  CAST(language_name AS STRING) AS language_name,
  CAST(project_type AS STRING) AS project_type,
  CAST(is_closed AS BOOLEAN) AS is_closed,
  CAST(_snapshot_fetched_at AS TIMESTAMP) AS _snapshot_fetched_at
FROM json.`${spark.wikicdc.raw_dim_wiki_reference_path}`;
```

No `CONSTRAINT ... EXPECT` (Section 4.1). Uses `json.\`path\`` (standard Spark SQL batch source) instead of `read_files` (Section 4.2), with explicit `CAST`s standing in for an explicit read schema, since the `json.\`path\`` shorthand can't take one directly. `${spark.wikicdc.raw_dim_wiki_reference_path}` is Spark SQL's own variable substitution, resolved from `spark-pipeline.yml`'s `configuration:` block (Section 8) — **this is a literal value in that file, not auto-populated from `.env`** (Section 4.3 explains why: a SQL file can't call `get_storage_backend()`, and `spark.conf.set(...)` is blocked inside pipeline registration, so there's no channel to pass a dynamically-resolved value from Python into a sibling SQL file). The `spark.wikicdc.` prefix is required, not stylistic — an unprefixed custom key is silently dropped by Spark's config loader (Section 4.3). Edit `spark-pipeline.yml`'s `configuration."spark.wikicdc.raw_dim_wiki_reference_path"` if your `BUCKET_NAME`/`STORAGE_BACKEND` differ from the committed local-MinIO default. This is the one asymmetry between the two variants — a direct consequence of the Python variant being able to call Phase 1's `StorageBackend` directly and the SQL variant not being able to.

`bronze_dim_wiki_reference` is a materialized view (batch, recomputed on refresh), not a streaming table — it doesn't need incremental checkpoint semantics for a handful of small, infrequently-updated snapshot files.

## 8. Pipeline spec (`pipelines/spark-pipeline.yml`, generated — not committed)

`pipelines/spark-pipeline.yml` is **not committed** — it's generated locally by `scripts/render_local_spark_config.py` from the committed template `pipelines/spark-pipeline.yml.example`, mirroring the `.env.example` → `.env` convention (9.8): the rendered file holds a machine-specific absolute path (`storage:`, which `spark-pipelines` requires as an absolute, URI-scheme path — a plain OS-env `${VAR}` placeholder doesn't work here, since the file is parsed as plain YAML with no env substitution — Section 4.3) and, for `s3`/`gcs` backends, values derived from real credentials.

```yaml
name: wikipedia_cdc_pipeline
storage: file://__PIPELINE_STORAGE_ROOT__   # filled in by the render script with an absolute path
libraries:
  # Relative to *this spec file's own directory* (pipelines/), not the repo
  # root or cwd — spark-pipelines resolves `include` against
  # spec_path.parent, so this is "bronze/**", not "pipelines/bronze/**".
  - glob:
      include: bronze/**
configuration:
  # "spark." prefix is required, not stylistic -- an unprefixed key is
  # silently dropped by Spark's config loader (Section 4.3).
  spark.wikicdc.raw_dim_wiki_reference_path: __RAW_DIM_WIKI_REFERENCE_PATH__   # only read by dim_wiki_reference.sql (Section 7.3); filled in via get_storage_backend().resolve_uri(...)
```

`name`/`storage` are required by `spark-pipelines` itself (undocumented in the original draft), and `libraries.glob.include` is relative to the spec file's own directory (also undocumented, and easy to get wrong — an `pipelines/bronze/**` include here silently matches zero files and later fails with `[RUN_EMPTY_PIPELINE]`). `raw_recentchange_path` is **not** here — `bronze_recentchange.py`/`dim_wiki_reference.py` resolve their own paths in Python (Section 4.3). Local Hive metastore persistence and the Hadoop `s3a`/`gs` connector are configured separately, via `SPARK_CONF_DIR`/`spark-defaults.conf` (Section 4.3, `docs/RUNBOOK.md`) — not in this file, since those are static, JVM-boot-time settings.

Silver and gold libraries are added to this same spec in their respective phases (Section 8 of `SPEC-phase3-silver-cdf.md` and `SPEC-phase4-gold-consumption.md`) — one pipeline spec, one DAG, growing per phase rather than one spec per layer.

## 11. Acceptance criteria (Given/When/Then)

1. **Consolidation without loss**
   Given N Parquet files available in raw, When `spark-pipelines run` executes, Then the total row count in `bronze_recentchange` matches the total row count in those N files.

2. **Automatic incrementality**
   Given `bronze_recentchange` already populated from a previous run, When new raw files arrive and the pipeline runs again, Then only the new files are processed — no duplicate rows for already-processed files. (Requires the persistent local metastore from Section 4.3 — without it, a second local run fails outright rather than reprocessing.)

3. **Reference dimension picked up on file arrival**
   Given a new snapshot file dropped into `raw/dim_wiki_reference/` by `fetch_wiki_sitematrix.py`, When the pipeline runs, Then `bronze_dim_wiki_reference` reflects the new snapshot's content.

4. **Portability**
   Given the same pipeline spec and source files, When run via `spark-pipelines run` locally and as a Lakeflow Declarative Pipeline on Databricks, Then both produce identical results, with no source-file change between environments. (True as implemented: Phase 2 uses no expectations/`read_files`/`create_auto_cdc_flow`, so there's no Databricks-only code path to diverge on.)

5. **Language-variant equivalence (`bronze_dim_wiki_reference` only)**
   Given the Python and SQL variants of `bronze_dim_wiki_reference`, When each runs independently against the same raw snapshot input, Then both produce identical content — confirming they're genuinely interchangeable, not just superficially similar. (`bronze_recentchange` has no SQL variant to compare against — Section 4.2.)

The original draft's acceptance criterion 5 ("fail-fast on structural corruption" via a named expectation) is dropped — Section 4.1.

## 13. Operating commands

```bash
# One-time (and after any .env change): generate the local Spark/Hadoop connector config (Section 4.3)
python scripts/render_local_spark_config.py

# Point Spark at that generated config for every command below
export SPARK_CONF_DIR="$(pwd)/local-stack/.spark-conf"

# Validate the pipeline definition without touching data
spark-pipelines dry-run --spec pipelines/spark-pipeline.yml
```
