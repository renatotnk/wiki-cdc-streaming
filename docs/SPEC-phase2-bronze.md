**Depends on:** `SPEC-agnostic-architecture.md` (`ComputeBackend`/`StorageBackend` contracts, principles P1–P8, conventions 9.1–9.4) and `SPEC-phase1-ingestion.md` (raw format and partitioning).

## 1. Objective

Read the raw Parquet files generated by Phase 1 and consolidate them into a bronze Delta table — typed, idempotent per partition, with Change Data Feed enabled, and runnable on both local Spark and Databricks with no code changes.

## 2. Scope

**In scope:**
- Reading the partitioned raw data (`dt`/`hour`) via `StorageBackend`.
- Applying an explicit schema (typing, no business validation rule), per `contracts/bronze_recentchange.contract.yaml` (P8).
- Idempotent writes to the bronze Delta table via `ComputeBackend`, with Change Data Feed enabled from table creation.
- Partition-parameterized execution (allows controlled reprocessing and backfill).

**Out of scope:**
- *Business* schema validation and routing of invalid rows (Phase 3 — bronze is a faithful mirror of raw, it does not filter by business rule).
- Consuming the Change Data Feed (that's Phase 3 — here we only enable the property on the table).
- Aggregations (Phase 4, deferred).

## 3. Why bronze isn't "just copying raw"

Bronze applies **typing** (light schema-on-write: `event_id: string`, `timestamp: bigint`, etc. instead of everything generic), but **applies no business rule**. If a raw file is structurally corrupted (not the expected schema at all), the bronze job must fail fast and loud (fail-fast, `ERROR` log) — not silence the problem. *Row-by-row* rejection based on business rules is exclusively Phase 3's (silver's) responsibility, per the architecture SPEC's P4 invariant. This keeps bronze simple (KISS): it mirrors and types, it doesn't decide what's valid.

## 4. Incrementality and idempotency strategy (this phase's key decision)

The bronze job uses **Spark Structured Streaming with a file source, triggered via `Trigger.AvailableNow`** — not a batch job with a manual partition, and not continuous streaming:

```python
(spark.readStream
    .format("parquet")
    .schema(bronze_schema)
    .load(raw_path)
    .transform(add_bronze_metadata)
    .writeStream
    .format("delta")
    .option("checkpointLocation", checkpoint_path)
    .outputMode("append")
    .trigger(availableNow=True)   # processes everything currently available, then stops — doesn't keep running
    .start()
    .awaitTermination())
```

Why this mechanism, and not `read()` + `replaceWhere` per partition:

- **Automatic incremental discovery:** the checkpoint (`checkpoint_path`) keeps track of which raw files have already been processed. There's no need to manually specify `dt`/`hour`, nor any external orchestration deciding "what's new".
- **Native idempotency:** Structured Streaming's file source guarantees exactly-once per file via the checkpoint — this replaces the need for a custom `replaceWhere`.
- **No continuous-streaming cost risk:** `Trigger.AvailableNow` processes the batch currently available and **stops on its own** — operationally the job behaves like a batch (you trigger it, it runs, it finishes), but with Structured Streaming's semantics and mechanism. No process stays active indefinitely waiting for future data.
- **Portability:** the file source is pure Spark — it works identically on `local[*]` and Databricks, without depending on Auto Loader (which is Databricks-exclusive and would break the architecture SPEC's agnosticism principle).

### 4.1 Why enable Change Data Feed on bronze even though it's append-only

Bronze only receives inserts in normal operation — at first glance it doesn't seem to need CDF. But there's a concrete technical reason to enable it anyway, at table creation:

```sql
CREATE TABLE bronze_recentchange (...)
USING DELTA
PARTITIONED BY (dt, hour)
TBLPROPERTIES (delta.enableChangeDataFeed = true)
```

Delta's `readStream` (used by Phase 3 to consume bronze incrementally) **fails by default** if the source table undergoes any change that isn't a pure append — an `UPDATE`, `DELETE`, or `MERGE` (e.g., a one-off fix to a batch with bad data, something that eventually happens in practice). Without CDF enabled, that correction would break Phase 3's incremental read on its next run. With CDF enabled from the start, this scenario is handled natively (Phase 3 sees the correction as a change event, not as a break). It's a low-cost decision now that avoids an expensive problem to discover later.

## 5. Data flow

```
raw_path (Parquet, Phase 1)
        │  spark.readStream.format("parquet").schema(bronze_schema).load(...)
        ▼
BronzeIngestor.transform(df)   # add_bronze_metadata + _bronze_loaded_at
        │
        ▼
writeStream.format("delta").trigger(availableNow=True)
        │  checkpoint at checkpoint_path controls what has already been read
        ▼
Delta table: bronze_recentchange (partitioned by dt, hour)
```

`BaseDeltaIngestor` (template method — defines the common flow, subclasses override the steps):

```python
# src/lib/ingestors/delta_ingestors.py
class BaseDeltaIngestor(ABC):
    """Common shape for any Spark Structured Streaming ingestor that reads from
    an incremental source and writes to a Delta table via Trigger.AvailableNow.
    Don't override run() — override the individual steps."""

    def __init__(self, compute: ComputeBackend, storage: StorageBackend, config): ...

    @abstractmethod
    def read_stream(self) -> DataFrame: ...

    @abstractmethod
    def transform(self, df: DataFrame) -> DataFrame: ...

    def write_stream(self, df: DataFrame) -> StreamingQuery:
        """Default: plain append + checkpoint + Trigger.AvailableNow.
        Subclasses override when they need a different strategy."""
        ...

    def run(self) -> IngestorRunResult:
        df = self.transform(self.read_stream())
        query = self.write_stream(df)
        query.awaitTermination()
        return self._build_run_result(query)  # from utils.py


class BronzeIngestor(BaseDeltaIngestor):
    def read_stream(self) -> DataFrame: ...          # readStream parquet + bronze_schema
    def transform(self, df: DataFrame) -> DataFrame:
        return add_bronze_metadata(df)               # from utils.py — typing only, no business rule
    # write_stream() uses the base default — bronze only appends
```

`IngestorRunResult` (a generic dataclass in `utils.py`, whose fields each subclass populates) replaces the earlier `BronzeRunResult` — the same object is reused by `SilverIngestor` in Phase 3.

## 9. Acceptance criteria (Given/When/Then)

1. **Consolidation without loss**
   Given N Parquet files available in raw (any partition, not yet processed), When `BronzeIngestor.run()` executes, Then the total number of new rows in the bronze table exactly matches the total number of rows in those N files.

2. **Automatic incrementality**
   Given the bronze table already containing data from a previous run, When new raw files arrive and the job runs again, Then only the new files are processed (verifiable via `batch_id`/`numInputRows` from `StreamingQueryProgress`) — already-processed files do not generate duplicate rows.

3. **Automatic termination (no continuous-streaming cost)**
   Given the job started with `Trigger.AvailableNow`, When there are no more new files to process, Then the process terminates on its own (returns from `awaitTermination()`) — no streaming process stays active waiting for future data.

4. **Compute portability**
   Given the same `BronzeIngestor` code, When I run it with `COMPUTE_BACKEND=local` and, separately, with `COMPUTE_BACKEND=databricks`, Then the result is identical in both cases, with no change to `src/lib/ingestors/` or `src/transform_bronze/`.

5. **Fail-fast on structural corruption**
   Given a raw file structurally incompatible with the expected schema, When `readStream` tries to apply the schema, Then the job fails with an explicit `ERROR` log (it does not silently write partial rows).

## 12. Local data inspection

With no local Unity Catalog, inspecting the bronze table uses one of the two options below (documented in `scripts/inspect_bronze.py`):

- **DuckDB (recommended default, no SparkSession needed):**
  ```sql
  SELECT * FROM delta_scan('path/or/s3a-gs-uri/bronze_recentchange') LIMIT 20;
  ```
  Can be plugged into any SQL GUI client (DBeaver, Harlequin) for visual exploration.

- **Local PySpark (when a session is already active, e.g., debugging the job):**
  ```python
  spark.read.format("delta").load(bronze_path).show()
  ```

No local Hive Metastore or Thrift Server is created — that would be disproportionate complexity (violates KISS) for a project this size. If it makes sense in the future to have a catalog experience closer to Unity Catalog locally, that's recorded as a possible extension, not a requirement of this phase.
