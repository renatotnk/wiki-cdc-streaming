# SPEC — Phase 2: Bronze (Spark Declarative Pipelines)

**Depends on:** `SPEC-agnostic-architecture.md` (`StorageBackend` contract, principles P1–P8, conventions 9.1–9.5.1) and `SPEC-phase1-ingestion.md` (raw format and partitioning).
**Does not redecide anything already fixed in those documents — only references them.**

---

## 1. Objective

Declare the raw Parquet files generated by Phase 1 as a bronze streaming table via Spark Declarative Pipelines (SDP) — typed, idempotent by construction, with Change Data Feed enabled — and add a second, genuinely external reference dimension (`bronze_dim_wiki_reference`) refreshed in batch whenever a new snapshot file arrives. Both run identically via `spark-pipelines run` locally and as a Lakeflow Declarative Pipeline on Databricks, in Python or SQL.

## 2. Scope

**In scope:**
- `bronze_recentchange` as an SDP streaming table reading the partitioned raw data.
- `bronze_dim_wiki_reference` as an SDP batch/streaming table reading periodic wiki-metadata snapshots from the Wikimedia sitematrix API.
- Explicit schema/type expectations for both, per `contracts/bronze_recentchange.contract.yaml` and the new `contracts/dim_wiki_reference.contract.yaml` (P8).
- Change Data Feed enabled on `bronze_recentchange` from table creation.

**Out of scope:**
- *Business* schema validation and routing of invalid rows (Phase 3 — bronze is a faithful mirror of raw, it does not filter by business rule).
- Consuming the Change Data Feed (that's Phase 3 — here we only enable the property on the table).
- Aggregations (Phase 4, deferred).

## 3. Why a second, external dimension source at bronze

Every dimension in the star schema so far (`dim_editor`, `dim_page`, `dim_wiki`) is *derived* entirely from the fact stream itself — there's no dimension coming from a genuinely independent source, which is a bit artificial next to a real Kimball scenario (where dimensions commonly arrive from different systems, on their own refresh cadence). `bronze_dim_wiki_reference` fixes that: it holds wiki metadata (language name, project type — Wikipedia, Wiktionary, Wikinews, etc.) sourced from the Wikimedia `sitematrix` API (`https://meta.wikimedia.org/w/api.php?action=sitematrix`), a real reference dataset independent of the `recentchange` event stream. `dim_wiki` in gold (Phase 4) is enriched by joining the stream-derived `wiki_code` against this table — a genuine conformed-dimension-from-a-second-source pattern, not just a label for the same data twice.

### 3.1 How new snapshots arrive and get picked up

`scripts/fetch_wiki_sitematrix.py` (a one-off/periodic script, not part of the pipeline itself) calls the sitematrix API and drops a timestamped JSON snapshot into `raw/dim_wiki_reference/`. `bronze_dim_wiki_reference` is declared as a batch table over that folder — every `spark-pipelines run` picks up any new snapshot file automatically (SDP's incremental file-source semantics, the same mechanism as `bronze_recentchange`, just triggered by an irregular/manual file drop instead of continuous producer output). No separate mechanism is needed for "batch on file arrival" — it's the same SDP dataset declaration pattern used for the streaming table, just over a folder that fills up occasionally instead of continuously.

## 4. Why bronze isn't "just copying raw"

Bronze applies **typing** (light schema-on-write) via SDP expectations, but **applies no business rule**. If a raw file is structurally corrupted, the pipeline must fail fast and loud — not silence the problem. This is expressed as a fail-on-violation expectation (`@dp.expect_or_fail`/`EXPECT ... ON VIOLATION FAIL UPDATE`), not a custom try/except. *Row-by-row* rejection based on business rules is exclusively Phase 3's (silver's) responsibility, per the architecture SPEC's P4 invariant.

## 5. Why SDP instead of hand-rolled Structured Streaming (recorded here, detailed in `trade-offs.md`)

Earlier drafts of this SPEC used a custom `BaseDeltaIngestor`/`BronzeIngestor` class with manual `readStream`/`writeStream`/`Trigger.AvailableNow`/checkpoint wiring. SDP replaces all of that: declaring `bronze_recentchange` as a streaming table gives the same incremental, checkpoint-backed, run-and-stop behavior natively, with less code to maintain — and, critically, SDP is genuinely open-source (Spark 4.1+, `pyspark.pipelines`/`spark-pipelines` CLI), so this doesn't cost anything in local/cloud portability (P1/P6). See `docs/trade-offs.md` for the full comparison.

## 6. Data contracts (bronze schemas)

Source of truth for `bronze_recentchange`: `contracts/bronze_recentchange.contract.yaml` (unchanged from the prior draft — inherits the Phase 1 raw fields, `_extra_fields`, `_schema_version`, typed per Section 6 of `SPEC-phase1-ingestion.md`).

New contract for `bronze_dim_wiki_reference`: `contracts/dim_wiki_reference.contract.yaml`.

| Field | Type | Description |
|---|---|---|
| `wiki_code` | `StringType` | Natural key, matches `wiki` in `recentchange` events |
| `language_name` | `StringType` | Full language name (e.g., "Portuguese") |
| `project_type` | `StringType` | `wikipedia`, `wiktionary`, `wikinews`, etc. |
| `is_closed` | `BooleanType` | Whether the wiki is closed/read-only |
| `_snapshot_fetched_at` | `TimestampType` | When `fetch_wiki_sitematrix.py` pulled this snapshot |

## 7. Pipeline definitions

Both variants declared side by side (convention 9.5.1) — pick one to keep once compared:

### 7.1 Python (`pipelines/bronze/bronze_recentchange.py`)

```python
from pyspark import pipelines as dp
from pyspark.sql.functions import current_timestamp

@dp.table(
    name="bronze_recentchange",
    table_properties={"delta.enableChangeDataFeed": "true"},
    partition_cols=["dt", "hour"],
)
@dp.expect_or_fail("valid_schema", "_event_id IS NOT NULL")  # fail-fast, Section 4
def bronze_recentchange():
    return (
        spark.readStream.format("parquet")
        .schema(bronze_schema)  # from pipelines/bronze/schema.py, shared with the SQL variant's contract
        .load(raw_recentchange_path)
        .withColumn("_bronze_loaded_at", current_timestamp())
    )
```

### 7.2 SQL (`pipelines/bronze/bronze_recentchange.sql`)

```sql
CREATE OR REFRESH STREAMING TABLE bronze_recentchange
(CONSTRAINT valid_schema EXPECT (_event_id IS NOT NULL) ON VIOLATION FAIL UPDATE)
PARTITIONED BY (dt, hour)
TBLPROPERTIES (delta.enableChangeDataFeed = true)
AS SELECT *, current_timestamp() AS _bronze_loaded_at
FROM STREAM read_files(
  '${raw_recentchange_path}',
  format => 'parquet',
  schema => '${bronze_schema_ddl}'
);
```

### 7.3 Python (`pipelines/bronze/dim_wiki_reference.py`)

```python
from pyspark import pipelines as dp

@dp.table(name="bronze_dim_wiki_reference")
@dp.expect_or_fail("valid_wiki_code", "wiki_code IS NOT NULL")
def bronze_dim_wiki_reference():
    return (
        spark.read.format("json")  # batch, not readStream — new snapshots arrive irregularly
        .schema(dim_wiki_reference_schema)
        .load(raw_dim_wiki_reference_path)
    )
```

### 7.4 SQL (`pipelines/bronze/dim_wiki_reference.sql`)

```sql
CREATE OR REFRESH MATERIALIZED VIEW bronze_dim_wiki_reference
(CONSTRAINT valid_wiki_code EXPECT (wiki_code IS NOT NULL) ON VIOLATION FAIL UPDATE)
AS SELECT * FROM read_files(
  '${raw_dim_wiki_reference_path}',
  format => 'json',
  schema => '${dim_wiki_reference_schema_ddl}'
);
```

`bronze_dim_wiki_reference` is a materialized view (batch, recomputed on refresh), not a streaming table — it doesn't need incremental checkpoint semantics for a handful of small, infrequently-updated snapshot files.

## 11. Acceptance criteria (Given/When/Then)

1. **Consolidation without loss**
   Given N Parquet files available in raw, When `spark-pipelines run` executes, Then the total row count in `bronze_recentchange` matches the total row count in those N files.

2. **Automatic incrementality**
   Given `bronze_recentchange` already populated from a previous run, When new raw files arrive and the pipeline runs again, Then only the new files are processed — no duplicate rows for already-processed files.

3. **Reference dimension picked up on file arrival**
   Given a new snapshot file dropped into `raw/dim_wiki_reference/` by `fetch_wiki_sitematrix.py`, When the pipeline runs, Then `bronze_dim_wiki_reference` reflects the new snapshot's content.

4. **Portability**
   Given the same pipeline spec and source files, When run via `spark-pipelines run` locally and as a Lakeflow Declarative Pipeline on Databricks, Then both produce identical results, with no source-file change between environments.

5. **Fail-fast on structural corruption**
   Given a raw file structurally incompatible with the expected schema, When the pipeline runs, Then the `valid_schema` expectation fails the update (`ON VIOLATION FAIL UPDATE` / `@dp.expect_or_fail`) — it does not silently write partial rows.

6. **Language-variant equivalence**
   Given the Python and SQL variants of `bronze_recentchange`, When each runs independently against the same raw input, Then both produce identical `bronze_recentchange` content — confirming they're genuinely interchangeable, not just superficially similar.

## 13. Operating commands

```bash
# Validate the pipeline definition without touching data
spark-pipelines dry-run --spec pipelines/spark-pipeline.yml

# Run it (local Spark 4.1+)
spark-pipelines run --spec pipelines/spark-pipeline.yml

# Fetch a new wiki-metadata snapshot (run whenever you want to refresh it)
python scripts/fetch_wiki_sitematrix.py

# Inspect data locally
python scripts/inspect_bronze.py
```
